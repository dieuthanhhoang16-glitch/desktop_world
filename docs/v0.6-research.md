## 一、widget 组织方式（短期·排版/组件层）

目标：动态桌面窗口目前是一张整版早报；长期它会变成「桌面 widget 面板」，
先借两个最成熟的桌面 widget 系统的组织方式，把结构提前拆对。

### Übersicht（macOS）— felixhageloh/uebersicht
- **要读**：widget 生命周期（command → refreshFrequency → render(style) → update）
  和托管窗口（一个桌面级 WebView 承载全部 widget）。
- **它证明了**：每个 widget 是独立文件，自带「取数命令 + 刷新周期 + 纯渲染函数」，
  宿主只管调度和摆位。
- **与我们对应**：`world/collector*.js` = command 层（已有）；`template/daily-card.html`
  的 render(R) = render 层（已有）；缺的是 **tile 化**——把统计区 / 专案区 / 看板列 /
  世界景观 / 灵感条拆成各自声明「依赖数据 + 刷新周期」的小组件，live.js 的 15 分钟
  全量刷就可以退化成「每 tile 按需刷」。

### Rainmeter（Windows）— rainmeter/rainmeter
- **要读**：skin 的 .ini 结构：`[Measure*]`（数据源，定 UpdateRate）与 `[Meter*]`
  （展示件，`MeasureName=` 绑定）严格分层，皮肤的共享变量/@include 机制。
- **它证明了**：数据层与展示层分文件、展示层只写绑定声明，是桌面 widget 最长寿的范式。
- **与我们对应**：watch / garden 已经是「measure」（按天结算、幂等快照）；
  share/text.js 与 daily-card.html 共用同一份 report，正好是「两个 meter 绑同一份 measure」，
  说明方向没错，继续把可插拔做到 tile 粒度即可。

**近期动作**：v0.6 立项时先画 tile 划分草图（不急着改代码）。

## 二、真·图标下方壁纸层（v0.6 主攻）

现状：动态桌面窗口浮在图标**上方**（world/live/live.js，见 v0.5 README 边界说明）。
两边各读一个成熟项目，Darwin/NT 各取一招，读完出评估再动手。

### macOS — sindresorhus/plash（MIT，Swift）
把任意网页设成桌面壁纸的单功能 app，正好等于「把我们的 render 层挂到图标下方」。
- **要读的核心招式**：浏览器窗口落到**桌面层**的 API 组合——
  `NSWindow.Level = kCGDesktopWindowLevel`（图标层之下）、`collectionBehavior`
  （跨 Spaces 静止显示）、`ignoresMouseEvents = true`。
- **顺带核对**：多屏/热插拔的回摆、全屏 Spaces 的共存、睡眠唤醒后的层级恢复、
  窗口 server 级 API（CGWindowLevel）在近年 macOS 的可用性警告。
- **落点评估**：Electron 能设 `type: 'desktop'`（Linux）但 macOS 层级的官方支持
  长期处于 PR 搁浅状态；如果 Plash 的招式映射不回 Electron 公开 API，
  选项是 (a) 原生 N-API 小模块只调窗口层级，(b) 与上游共建 desktop 层支持。

#### Plash 源码实读结果（2026-10-05，官方仓库已闭源清历史 → forks API 找到 peterlyoo/Plash 完整快照）

`DesktopWindow.swift` 全文实读，配方集齐且极简：

```swift
level = NSWindow.Level(rawValue: Int(CGWindowLevelForKey(.desktopWindow)))
isOpaque = false; backgroundColor = .clear      // 透明底色
isRestorable = false; canHide = false
ignoresMouseEvents = true                        // 点击穿透（治本，无需 hit-test 绕路）
collectionBehavior = [.stationary, .ignoresCycle, .fullScreenNone]
// .stationary = 钉在所有 Space；.ignoresCycle = 不进 Cmd+Tab轮换；.fullScreenNone = 不纠缠全屏空间
webView.setValue(false, forKey: "drawsBackground") // WKWebView 透底，让透明层露出桌面
// 交互模式（可编辑网页时）：level 升到 .desktopIcon+1、ignoresMouseEvents = false —— 一升一降即切换
```

⚠️ 新 SDK 差异：`NSWindow.Level.desktop` 糖在新 SDK 里没有了，须回退到公开常量
`CGWindowLevelForKey(.desktopWindow)`——本机（macOS 26 / Swift 6.3.3）实测 rawValue = **-2147483623**，
老文档里的 -2147483624 已过期；图标层 `CGWindowLevelForKey(.desktopIconWindow)` = **-2147483603**（+20 的整数差，
正是「窗口在图标下方」的秩序保证）。

#### PoC 验证结果（`world/live/poc/desktop-wallpaper.swift`，编制/复验 2026-10-05）

- 编译：`swiftc -O ... -framework Cocoa -framework WebKit`，零警告；
  两个已修坑：①`.desktop` 糖缺失（上条）；②`NSApplication.delegate` 是 **weak**，顶层必须 `let pocDelegate` 强引用。
- 运行：`/tmp/dwpoc &`（accessory policy 不进 Dock），全屏边框窗口落到桌面层并渲染
  `world/out/.daily-card.render.html`。
- **程序化证据**（`world/live/poc/window-layer-check.swift`，公开 API `CGWindowListCopyWindowInfo`）：
  `pid=68021 layer=-2147483623` == 本机 kCGDesktopWindowLevel，比图标层低 20 级 → ✅ **落在图标下方的桌面层**。
  （验证器自身教训：`.excludeDesktopElements` 会把桌面层窗口和目标一起滤掉；断言也**别硬编码**常量，
  直接用 `CGWindowLevelForKey` 动态值。）
- 点击穿透：`ignoresMouseEvents = true` 与 Plash 生产版逐字一致（该属性无私有回读 API，
  以 Plash 实际出货 + 窗口不可 becomeKey/Main 佐证）；最终由用户目检一锤定音。
- **结论：Plash 招式在 macOS 26 全部可用、无私有 API、无 warning。**

残项：多屏/热插拔回摆、睡眠唤醒层级恢复、`screencapture` 截图被拒（本机未授屏幕录制权限，目检由用户完成）。

### Windows — rocksdanister/lively（GPL-3.0，C#）
业界事实标准的动态壁纸方案，核心就是 WorkerW 挂窗。
- **要读的核心招式**：给 `Progman` 发 `0x052C` 消息催出隐藏的 `WorkerW`
  （`SHELLDLL_DefView` 的兄弟窗口），把渲染窗口 `SetParent` 到它下面，
  使壁纸位于图标之下、任务栏之上。
- **顺带核对**：Win10/Win11 桌面窗口结构差异、多屏各自 WorkerW、
  「全屏应用时暂停/省电策略」这类产品级细节（省电逻辑我们的 live 刷新也用得上）。
- **⚠️ 授权自律**：Lively 是 GPL-3.0，用户取向是「无合同风险的成熟参照」——
  **读招式、抄 API 时序，不抄实现代码**；Plash（MIT）相对宽松，同样只借思路。

## 三、皮肤动画拆分（芽芽 v2 素材管线）

### Shimeji-ee — Kilkakon/shimeji-ee（及各语言 fork）
桌面宠物动画的事实前辈，配置驱动。
- **要读**：`conf/` 的动作定义——**Action = 命名状态**（Walk/Sit/Climb...）；
  每个 Action 由若干 Animation 组成，**Animation = Pose[]，每 Pose 三件套
  （图片 + 锚点 anchor + 时长 duration）**；另有 Behavior 状态机负责
  环境感知（走到屏幕边缘爬墙、重力下落）。
- **它证明了**：素材层（姿势帧序列+每帧时长+锚点）与行为层（状态机+环境规则）
  解耦，美术只管帧、程序只管切换。
- **与我们对应**：theme.json 的 states/files/timings 已是同构——芽芽 v2
  直接把「生长反应」（升级进化、浇水、连击连发）定义成 Action 组即可，
  不需要为生长发明新动画格式。

### APNG 制作约定（以 Calico 实样为准，2026-10-05 脚本核实）

读 acTL chunk 实测 `themes/calico/assets/` 全部 27 个 APNG（均为动画）：

| 口径 | 实测 | 备注 |
|---|---|---|
| 帧数分布 | **12–64 帧，中位 41** | 常驻状态（idle/working/dozing）41 帧 ≈ 1.7s@24fps；反应类（react/mini-alert）28–33 帧；过场类（mini-enter/mini-peek）12–22 帧；口气大的（typing/yawning）61–64 |
| 单文件体积 | ≤ **800KB**（最大 happy 720KB / typing 800KB） | 平均 423KB |
| 全套体量 | 27 文件共 **11.2MB** | 打包进 asar 无压力 |
| 缩放约定 | **最近邻** `image-rendering: pixelated` | ✅ 已核实：引擎全局 `src/styles.css:144`；素材内不嵌缩放逻辑（codex-pet 适配器反例用 `auto`） |

⚠️ **与先前口述口径的出入**：「约 16–21 帧 / ≤8MB」与 Calico 实样不符——
实样更宽松、且按状态类型分档（常驻 41 / 反应 ~30 / 过场 ~15）。
芽芽 v2 的制帧预算按实测分档走：**常驻 40 上下、反应 30 上下、过场 20 以内；
单文件 ≤800KB、全套 ≤12MB、最近邻放大（引擎已保）**。
